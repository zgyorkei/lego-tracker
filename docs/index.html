What Brick Tracker is

Brick Tracker is a wishlist and price tracker for LEGO sets. You add a set by its number; the app looks up the official name, picture and LEGO price, then checks the shops you choose (Amazon, BrickLink, Arukereso or any shop you add) and shows where each set is cheapest and how far below the official price it is. Over time it records a price history per set, so you can tell a real discount from the usual price.

When you buy, mark the set as purchased at what you paid, in any currency: the app converts at that day's exchange rate and keeps a running total of what you saved. Share a gift registry with family so nobody buys the same set twice, tick off collectible minifigures, and let other apps read your planned sets through a small JSON API.

It runs as a website on any device, installable as an app on Android, ChromeOS and Googlebooks. An optional Windows app reads the shop pages with a real browser on your own connection, so prices are checked without any AI, refreshes everything every morning at 4AM, and does the fetching for the website too, whichever device you press refresh on.

How it works

Three parts, each optional beyond the first. Your data lives in your own Firebase project, under your Google account.

Any device

The website

  • A React app, also installable (PWA)
  • Sign in with Google
  • Its server (Vercel) looks sets up on Brickset, BrickLink and LEGO.com, and asks Gemini for shop prices when no desktop app is running
Your Firebase project

Firestore

  • Your sets, price history and price sources, private to your account
  • Live: a change on one device shows on all of them at once
  • The meeting point of website and desktop app
  • Public only where you share: registries and the Planned Sets API
Optional, Windows

The desktop app

  • The same app, plus a real browser (Playwright, Chromium)
  • Reads shop pages itself: no AI
  • Refreshes daily at 4AM, sits in the tray
  • Picks up refreshes the website hands it
Pressing refresh on the website with the desktop app running: the website writes a request to Firestore, the desktop app claims it, reads the shops, and the new prices appear on every device.
With no desktop app running, the website's server asks Gemini (with Google Search) for the shop prices instead, and reads BrickLink directly.

Where AI is used

Only for shop prices and set details on the website when no desktop app is running, and once per shop when the desktop app learns a new one. Everything else is read straight from the source.

What you need

  • To use it: a browser (Chrome, Edge, Firefox, Safari) and a Google account. Install it as an app from Chrome on Android, ChromeOS or a Googlebook.
  • To run your own copy: a GitHub account, a Firebase project, a Vercel account and a Gemini API key. About an hour, following the setup guide.
  • For the desktop app: Windows 10 or 11, Node.js 20 or newer to build it, and about 1 GB of disk for the app and its bundled browser.
The app

Features

Everything here works on the website, on every device. Where the desktop app does something differently, it says so.

01

Your sets

Dashboard

No AISynced

Every set you plan to buy or have bought, as a card with its picture, the official LEGO price and the market prices.

  • Filter All, Planned or Purchased; sort by date added, priority, set number or name.
  • Totals at the top: the official value of what is planned and bought, what you paid, and what you saved.
  • Priorities (high, medium, low) and quantities per set.
  • Prices shown in any of 13 currencies (HUF, EUR, USD, GBP, CHF, PLN, CZK and more), converted at the day's rate.
  • Themes inspired by LEGO lines (Classic Space, Star Wars, Ninjago and more), from the palette button.

Adding a set

No AI first

Type the set number; the name, picture and official Hungarian LEGO price fill in by themselves.

  • Looked up on Brickset and LEGO.com. The desktop app reads LEGO.com in a real browser and takes LEGO's own English name and product photo.
  • Leaked and unannounced sets are marked provisional; on the website, Gemini finds their details and expected release date on fan sites.
  • Promotional items that neither LEGO.com nor Brickset know get their name and picture from a shop listing that has them.
  • Collectible minifigure series get their figure list automatically.

On your phone, Chromebook or Googlebook

Installable

The website adapts to small screens and installs as an app with its own icon and window.

  • In Chrome: the menu's Install app or Add to home screen; on ChromeOS and Googlebooks, the install icon in the address bar.
  • Opens instantly, even before the network answers; every deploy shows at once.
  • When the desktop app is running at home, a refresh pressed on the phone is done there, without AI.
02

Prices

Market prices

No AI on desktopGemini on the website alone

One tile per shop: the price, converted to your currency, and how far it is from the official price.

  • 30% or more below the official price turns the tile green: a great deal.
  • Each tile links to the listing; click the price to mark the set as bought at it.
  • Refresh one set, or all of them with Update all. With the desktop app running, both are done there.
  • The right product, or none: listings that only mention the set number (light kits, display cases, minifigure packs) are skipped, and a set the shop does not sell itself shows no price rather than a reseller's used offer.

BrickLink, the honest way

No AI

BrickLink's price is the cheapest new lot that is sealed or complete, read lot by lot.

  • BrickLink's summary "minimum price" mixes in incomplete and used lots: a set at 5 EUR is usually "speeder only, no minifigures". Brick Tracker reads every lot instead.
  • Lots marked incomplete are skipped, and so are lots marked complete whose description admits missing parts or figures, which sellers do surprisingly often.
  • The tile says which it is: New (sealed) or New (complete).

Your price sources

Synced

Amazon EU, BrickLink and Arukereso to start with; add up to fifteen shops of your own by their search address.

  • A source is a name, a search URL with {setNumber} where the number goes, a currency and a chart colour.
  • Saved to your account, so every device and the desktop app use the same list.
  • In the desktop app each source shows how it is read: built-in rules, taught, or not taught yet. See teaching a new shop.

Price history

No AISynced

Each refresh stores every shop's price; the chart under the price tiles shows the lowest over time.

  • Prices are kept both in the shop's own currency and converted to forints, so shops in different currencies chart on one axis.
  • The desktop app's 4AM refresh adds one reading a day, so the history fills in without you doing anything.
03

Collection

Purchases and savings

No AISynced

Mark a set as purchased with the price, the currency and the day; the app does the rest.

  • Paid in euros or dollars? The price is converted at the exchange rate of the purchase day.
  • The dashboard totals what you paid against the official prices: your savings so far.
  • Change the day later, or move a set back to planned.

Minifigure checklists

No AI first

For collectible series, flip the card to a checklist of every figure.

  • Star the figures you want, tick the ones you have; the card shows how many are still wanted.
  • The wanted figures show on your gift registry too.
04

Sharing

Gift registry

Public link

Pick sets for a wishlist and send the link. Family can see the best prices and reserve a gift, without an account.

  • First reservation wins, so nobody buys the same set twice.
  • Only what a gift-giver needs is shared: names, pictures, best prices and wanted figures. Never what you paid, never your account.
  • Several registries side by side (birthday, Christmas), each with its own link.

Planned Sets API

JSONKept in sync

A private link that returns your planned sets, with every shop's price, and your purchases, as JSON for other apps.

  • Create it from the API button (Planned filter). The random token in the link is the only key: delete the link to revoke it.
  • Kept up to date automatically whenever your sets change; responses are cached for a minute; open to browsers (CORS).
  • Purchases carry the day, the price paid and the official price, which a budgeting app can book as expenses.

Windows

Desktop app

The same app, with a real browser of its own. It checks prices without AI, refreshes every morning, and does the fetching for the website whenever it is running.

What it adds

  • Prices without AI. Shop pages are read the way you would read them, in a browser on your own connection, instead of asking Gemini to look them up.
  • A daily refresh at 4AM, or at the first start after it if the PC was off. Nobody needs to open anything.
  • Work for the website. Press refresh on your phone and the desktop app at home does it; see the hand-off.
  • New shops, learnt once. Teach it any shop's search page; see teaching.
  • Everything else is identical: the same screens, the same account, the same data, live.

Reading shops with a real browser

Shops guard their pages against bots. Each of these settings came from a live trial, and each one gets past a real block.

SettingWhy
Its own Chromium (Playwright), shipped with the appWorks the same on every PC, independent of the installed browser and its policies.
A real browser window, parked off-screenCloudflare's check (Arukereso) never clears for a headless browser, but clears at once for a real window. Nothing appears on screen.
English browser languageAmazon.de blocks or blanks the page for some browser languages; the display currency is pinned separately.
A persistent profile, one page at a time, with pausesConsent and clearance cookies survive between runs, and the shops see a person-paced visitor, not a burst.

Matching is strict: the title must carry the set number where shops put a set's own code, accessories are excluded, and when a set's own listing has no price the answer is "no price", never the next product down the list.

The 4AM refresh

Every day at 4AM local time the desktop app refreshes the market prices of your sets and adds the day's reading to their history. If the PC was asleep or off, it runs at the next start. With the app signed in on several machines it still runs once: the day's run is a shared request that the first machine to claim it carries out.

Set details from LEGO.com

Adding a set in the desktop app reads LEGO.com in the browser first: the official HUF price and the product photo from the Hungarian page, and LEGO's English name from the US page. Brickset fills only the gaps, and covers sets LEGO.com does not list. No AI is involved.

Teaching a new shop

Any shop with a search page can become a price source.

Gemini, once per shopDesktop app
  1. Add the shop in Price Sources with its search address, {setNumber} where the number goes, and press Teach.
  2. The app opens that search page for three of your planned sets in its browser and keeps a compact copy of each.
  3. Gemini writes reading instructions from them: which elements are the products, their titles and prices, and how numbers are written.
  4. The instructions are run on the same live pages; if they find nothing, Gemini gets one retry with what the test saw.
  5. You see the prices found and choose Save or Discard. Saved instructions sync to every device.

Why data, not code: a shop page could try to trick the AI. Instructions can only point at elements and read their text, so nothing a page says can make the app run anything.

Tray, startup and updates

  • Closing the window keeps the app in the tray, so the 4AM refresh and the website's requests still happen. Quit from the tray menu.
  • It starts with Windows, straight into the tray; the tray menu's Start with Windows turns that off.
  • Sign-in opens Google in your normal browser, because Google does not allow signing in inside embedded browsers.
  • To update, quit from the tray and run the new build's install.cmd.

What stays on your PC

  • The Gemini key (used only for teaching) is kept in Windows Credential Manager; the sign-in client file sits in %APPDATA%\Brick Tracker. Neither is ever part of a build.
  • The app's server listens on this PC only (localhost), never on the network.
  • The browser profile it reads shops with is its own, separate from yours.
Data

Sync

How your data moves between devices, between the website and the desktop app, and out to other people and apps.

Live sync between devices

Your sets, their price history and your price sources are stored in Firestore under your Google account. Every open copy of the app listens for changes, so a set added on the phone, a price refreshed on the desktop, or a source taught on another PC shows everywhere within a second or two. Access is enforced by Firestore's security rules: nobody else can read or change your sets.

The desktop does the website's work

While the desktop app runs, the website hands it every refresh instead of asking Gemini.

  1. The desktop app writes an "I'm online" signal to Firestore every 2 minutes.
  2. You press Update all, or refresh a card, on any device. The website writes a request: which sets, and whether details, prices or both.
  3. The desktop app claims the request and runs its normal local-browser refresh. The website shows "Refreshing in the desktop app (local browser, no AI)".
  4. The new prices arrive on every device through live sync, and the request is cleared.

The website falls back to Gemini when the desktop app has not been seen for 5 minutes, does not pick the request up within 45 seconds, or reports a failure. Claiming and cancelling are Firestore transactions, so a request is never done twice.

Several desktops

Sign the desktop app in on more than one Windows PC with the same Google account and they share the work: each request is claimed by exactly one of them, and the 4AM refresh runs once a day, on whichever machine claims it. Moving to a new PC is just installing and signing in there.

Other apps: the Planned Sets API

The app keeps a public snapshot of your planned sets and purchases, at a link with a random token, up to date whenever your sets change. Other apps read it as JSON at /api/planned-sets/<token>; see the feature. Deleting the link revokes access at once.

Share links

Gift registries are public by their link, like the API: only the fields a gift-giver needs are copied into the registry, and reservations are written by visitors, first come first served. Links always point at your own deployment.

Offline

The installed app opens without a network, from its cached files, and shows the sets the browser last saw; fetching prices and syncing need a connection again.

Setup guide

Run Brick Tracker for yourself and your family: your own Firebase project for the data, Vercel for the website, and optionally the Windows desktop app. About an hour, most of it clicking through consoles.

What you will set up

You need Node.js 20 or newer and Git on your computer for steps 1 and 4, and Windows for step 7.

Get the code

  1. Fork github.com/zgyorkei/lego-tracker to your GitHub account (the Fork button).
  2. Clone your fork and install the dependencies:
git clone https://github.com/<you>/lego-tracker.git
cd lego-tracker
npm install

Firebase: sign-in and the database

  1. At console.firebase.google.com, Create a project (Google Analytics is not needed).
  2. Authentication → Get started → Sign-in method → enable Google, choose a support email, save.
  3. Firestore Database → Create database, in production mode, in a region near you (for Europe, eur3 or europe-west). Note its name: usually (default).
  4. In Firestore's Rules tab, replace everything with the contents of firestore.rules from the repository, and Publish. Do this again whenever that file changes.
  5. Project settings (the gear) → Your apps → add a Web app. Copy the firebaseConfig values it shows: they become the VITE_FIREBASE_* variables below. They are not secret; the rules protect the data.

If your database is not named (default), set VITE_FIREBASE_DATABASE_ID to its name, and pick that database in the console before pasting the rules: rules are per database.

Only your accounts, optionally. Anyone with a Google account can sign in to your site and keep their own list there, using your quota. To allow only yourself and your family: in Firestore, Start collection access, document ID allowlist, with a field emails of type array holding each Google address in lower case. The rules then refuse every other account, and the app signs it out with a message. Gift-registry links keep working for everyone. Edit the list there to add someone; delete the document to open the site again.

A Gemini API key

  1. At aistudio.google.com/apikey, Create API key, in the Google Cloud project Firebase made (it is listed by the same name).
  2. Keep it for the GEMINI_API_KEY variable. It only ever goes into the server's environment, never into the website's code.

Without a key the app still works: BrickLink, Brickset and LEGO.com need none, and with the desktop app running no shop price needs AI either. Only the website's own price checks, and teaching new shops, use it.

Run it locally

Create a file named .env in the repository folder (it is ignored by Git), from .env.example:

GEMINI_API_KEY=your-gemini-key
VITE_FIREBASE_API_KEY=...
VITE_FIREBASE_AUTH_DOMAIN=your-project.firebaseapp.com
VITE_FIREBASE_PROJECT_ID=your-project
VITE_FIREBASE_STORAGE_BUCKET=your-project.firebasestorage.app
VITE_FIREBASE_MESSAGING_SENDER_ID=...
VITE_FIREBASE_APP_ID=...
VITE_FIREBASE_DATABASE_ID=(default)
npm run dev      # http://localhost:3000

Open localhost:3000 and sign in with Google; localhost is allowed by Firebase out of the box. Add a set to check that lookups and saving work.

Deploy the website (Vercel)

  1. At vercel.com/new, import your fork. Vercel detects the Vite preset: build command npm run build, output directory dist. vercel.json makes /api a serverless function.
  2. Under Environment Variables, add every line of your .env. Optionally set VITE_PUBLIC_APP_URL to your final address (for example https://bricks.example.com).
  3. Deploy. Optionally add your own domain under Settings → Domains.
  4. Back in Firebase: Authentication → Settings → Authorized domains → add your Vercel address (your-project.vercel.app) and your own domain. Without this, Google sign-in is refused there.

Every push to your fork's main deploys again by itself.

Install it on your devices

  • Android: open your address in Chrome, menu → Install app (or Add to home screen).
  • ChromeOS, Googlebook, Windows or Mac: Chrome or Edge's install icon at the right of the address bar.
  • iPhone and iPad: Safari → Share → Add to Home Screen.

If the Google sign-in window is blocked on a phone, allow pop-ups for your site and try again; the sign-in screen says when this happens.

The desktop app optional, Windows

a. A sign-in client. In the Google Cloud console, open the project Firebase created:

  1. APIs & Services → OAuth consent screen: it already exists for Firebase's web sign-in. Make sure its publishing status is In production (in "Testing", sign-ins expire every 7 days). The app only asks for name and email, so no Google review is needed.
  2. Credentials → Create credentials → OAuth client ID → type Desktop app → Create → Download JSON.

b. Get the installer. It carries no Firebase project, yours or anybody's: each install is connected to a project in its own setup window (step d), so the same build works for everyone.

Download for Windows  zip, about 350 MB (all releases)

Or build it yourself from your fork; it needs no .env:

cd desktop
npm install
npx playwright install chromium
npm run dist

This builds the website, bundles Chromium, and writes desktop\release\<version>-<date>\ with the app, install.cmd and a zip of both.

c. Install it. Unzip it and run install.cmd (no admin rights needed). It copies the app to %LOCALAPPDATA%\Programs\Brick Tracker, adds a Start menu shortcut, makes it start with Windows, and starts it. The app is not code-signed, so Windows SmartScreen may warn the first time: More info → Run anyway.

d. Connect it. The first start opens the setup window:

  • Firebase config: paste the firebaseConfig snippet from step 2 as the console shows it, and the database ID if it is not (default).
  • Website address: your site from step 5 (for example https://bricks.example.com). Gift-registry and Planned Sets links point there, since the app itself runs on localhost, which nobody else can open.
  • Google sign-in client: choose the JSON downloaded in step a.
  • Gemini API key, optional: only for teaching new shops. It is kept in Windows Credential Manager, never in a file or a build.

The settings are saved in %APPDATA%\Brick Tracker. The tray menu's Settings... opens the window again; saving restarts the app.

e. Sign in. Login with Google: Google opens in your normal browser; approve, and you are signed in. From then on the app lives in the tray, refreshes at 4AM, and does the website's refreshes while it runs.

If you build from a terminal inside VS Code, npm start and install.cmd already cope with VS Code's ELECTRON_RUN_AS_NODE variable; other Electron tools may need it cleared.

Updating

  • Website: sync your fork with the original on GitHub (Sync fork); Vercel deploys it. If firestore.rules changed, paste it into the Firebase console again.
  • Desktop app: download the newest release (or pull and run npm run dist in desktop again), quit the app from the tray, and run the new install.cmd. Your sign-in and settings are kept.

Troubleshooting

What you seeLikely cause and fix
Google sign-in fails on the deployed site, but works on localhostThe address is not in Firebase's Authorized domains (step 5).
"Allow pop-ups for this site" on the sign-in screenThe browser blocked Google's window: allow pop-ups for your address.
"You do not have access to this data", or price sources not savingThe Firestore rules in the console are older than firestore.rules: paste and publish them again, in the right database.
